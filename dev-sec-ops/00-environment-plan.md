# План сборки окружения DevSecOps

Дата подготовки: 2026-10-05. Статус: проект учебного стенда.
Аудитория: один учащийся, знакомый с Linux, SSH и Git.

## Цель

Постепенно собрать стенд, на котором можно выпускать приложение, добавлять проверки безопасности и доказывать, что они работают. Первый практический компонент — Jenkins. Перед ним нужны Linux VM, SSH и Docker.

## Порядок сборки

| Этап | Что собираем | Когда этап завершён |
| --- | --- | --- |
| 0 | Отдельная Linux VM, доступ по SSH, Docker Engine и Compose | Docker запускает тестовый контейнер, версии записаны |
| 1 | Jenkins controller и отдельный build-agent | Agent Online, положительный pipeline успешен, намеренная ошибка останавливает сборку |
| 2 | Учебное приложение и Jenkinsfile в Git | Checkout, тесты и сохранение артефакта проходят на agent |
| 3 | Сборщик контейнеров и registry | Выпускается образ с зафиксированным digest; права публикации ограничены |
| 4 | SAST, SCA, secret scanning и проверка образа | Дефект обнаруживается; сбой сканера не считается успешной проверкой |
| 5 | Отдельный Kubernetes-стенд | Приложение развёрнуто; права CI и workload проверены |
| 6 | DAST и policy as code | Проверки выполняются на тестовой среде и блокируют контрольные нарушения |
| 7 | SBOM, подписи и provenance | Подмена артефакта или недоверенное происхождение блокируют выпуск |
| 8 | Runtime detection и восстановление | Учебное событие обнаружено; сервис восстановлен с доказательствами |

Для этапов 0–1 подготовлено [задание Jenkins](01-jenkins-setup.md). Учащийся сам находит официальную документацию, пишет инструкцию и собирает стенд — лично либо с AI-агентом. Остальные строки — план последующих лабораторных, а не уже реализованные компоненты.

## Вариант конфигурации для планирования

- Чистая Linux VM x86_64. Например, Ubuntu Server 24.04 LTS; поддержку выбранной ОС проверяет учащийся.
- Рекомендуемый старт для нашего стенда: 4 vCPU, 8 GiB RAM, 60 GB диска. Это запас для обучения, а не официальный минимум Jenkins.
- Windows-компьютер может использоваться как рабочее место: SSH запускается из PowerShell, команды установки — внутри Linux VM.
- Возможный маршрут — официальные контейнеры Jenkins. Совместимую Java и версии выбирает учащийся по документации; при контейнерном запуске Java входит в образ.
- Controller управляет заданиями, отдельный контейнер agent выполняет shell-команды. У controller 0 executors.
- Веб-интерфейс привязан к loopback VM и доступен через SSH-туннель. Agent подключается внутри Docker-сети через WebSocket.
- Данные controller и workspace agent хранятся в разных volumes. Docker socket и каталог controller не передаются agent.

Два контейнера на одном хосте подходят для доверенного однопользовательского стенда. Для исполнения произвольных внешних PR нужны отдельные одноразовые workers и более строгая изоляция. На первом этапе запускаем только собственные задания.

## Почему Kubernetes пока не нужен

Jenkins может работать независимо от Kubernetes. Сначала проверяем управление заданиями, выполнение на agent и сохранность данных. Кластер добавляется, когда появится приложение, готовое к развёртыванию. Это позволяет различать ошибки CI и ошибки оркестратора.

SonarQube, registry, Kubernetes, mesh и системы мониторинга не нужно устанавливать одновременно. Каждый компонент появляется вместе с задачей и критерием проверки.

## Что зафиксировать после установки

В отчёте о стенде указать ОС, архитектуру, версии Docker и Compose, Jenkins core, Java, digest обоих образов и версии плагинов. Сохранить ID двух smoke-сборок: успешной и намеренно неуспешной. Не прикладывать пароли, agent secret, полный вывод переменных окружения или резервную копию Jenkins.

## Учебный подход

Курс задаёт цель, ограничения и признаки готовности. Поиск официальных инструкций и сборка собственной последовательности действий входят в работу учащегося. Ручной и AI-маршрут имеют одинаковую приёмку. Наш анализ референсов: [разбор примеров KodeKloud](90-kodekloud-review.md).
