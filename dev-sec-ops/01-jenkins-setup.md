# Лабораторная 01 — самостоятельно собрать Jenkins

Дата: 2026-10-05.
Статус: спецификация лабораторной; развёртывание конкретного стенда ещё не проверено.
Предпосылки: основы Linux, SSH, Git и понимание контейнеров при выборе контейнерного маршрута.
Ориентир по времени: 4–8 часов для учащегося с указанной подготовкой; фактическое время зависит от выбранной среды.

## Цель

Найти актуальную официальную документацию, самостоятельно составить инструкцию установки, развернуть Jenkins и проверить, что задания выполняются на отдельном build-agent.

Готовые команды установки здесь намеренно не приведены. Собственная инструкция со ссылками и доказательствами — один из результатов лабораторной. Выполнять работу можно самостоятельно, с AI-агентом или комбинировать оба способа. Критерии зачёта одинаковы.

## Исходная задача

Нужна первая часть учебной платформы DevSecOps: controller Jenkins управляет заданиями, отдельный agent выполняет их. В дальнейшем на этой платформе появятся приложение, проверки безопасности и доставка в Kubernetes. Сейчас необходимо получить минимальный понятный стенд.

Выберите отдельную учебную Linux VM и способ установки, который поддерживается официальной документацией. Для первого опыта можно рассмотреть контейнеры controller и agent на одной VM. Установка пакетами также допустима, если выполнены требования к разделению доступа.

Планировочный ориентир для двух небольших компонентов: 4 vCPU, 8 GiB RAM, 60 GB диска. Это наш запас для лабораторной, а не официальный минимум. Сверьте требования выбранного способа установки и объясните свой выбор.

## Что нужно найти в первоисточниках

Найдите документы самостоятельно через поиск и навигацию сайтов проектов. Начальные направления поиска:

| Вопрос | Владелец документации | Что извлечь |

Проверяйте принадлежность сайта и репозитория проекту. Блог, видео, поисковый сниппет и ответ AI могут помочь найти оригинал, но не заменяют чтение нужного раздела официальной документации.

Не выбирайте автоматически самый свежий пример из выдачи. Он может относиться к weekly-выпуску, другой ОС или несовместимой версии Java.

## Этап 1 — составить собственную инструкцию

До установки создайте `installation-plan.md`. В нём должны быть:

1. Описание целевой машины и подтверждение, что это выделенная учебная среда.
2. Выбранный способ запуска и короткое сравнение с одной альтернативой.
3. Согласованный набор версий ОС, Jenkins, Java, agent и платформы запуска.
4. Схема соединений: откуда пользователь открывает UI и как agent достигает controller.
5. Порядок установки, проверки после каждого шага и ожидаемые результаты.
6. Перечень действий с повышенными правами и объяснение их необходимости.
7. Способ остановки, сохранения данных и безопасного повторного запуска.

Для каждой важной команды укажите источник и объясните, что она меняет. Если команда составлена вами или AI из нескольких примеров, отметьте это и опишите способ её проверки. Команды из документации сначала соотнесите со своей ОС и выбранными версиями.

## Этап 2 — собрать минимальный стенд

Реализуйте свой план. После ошибки не продолжайте зависимые этапы, пока не понятна причина. Записывайте исправления в собственную инструкцию, чтобы другой учащийся мог повторить результат.

Обязательные свойства:

- Сборки выполняются на отдельном agent; у built-in node controller — 0 executors.
- Agent запускает задания не от root и не имеет доступа к каталогу данных controller.
- У agent нет неограниченного sudo, доступа к Docker socket хоста или privileged-режима. На этом этапе сборщик контейнеров не требуется.
- Доступ к UI ограничен выбранным учебным способом. Допустим SSH-туннель; общий сетевой доступ требует обоснованной защиты соединения и авторизации.
- Нет анонимного административного доступа и общеизвестного пароля.
- Секреты не попадают в Git, отчёты, команды с публичным выводом и переписку с AI.
- Версии записаны; для контейнерного маршрута образы закреплены digest.
- Данные controller сохраняются при обычном перезапуске.

Изоляция процессов или контейнеров на одной VM подходит для собственных доверенных заданий. Запуск произвольных внешних PR выходит за рамки этой лабораторной.

## Этап 3 — доказать работоспособность

Самостоятельно создайте минимальный Pipeline по документации. Готовый Jenkinsfile не выдаётся.

Pipeline должен:

1. Выполнить shell-задачу на выбранном agent.
2. Показать имя узла и UID процесса, не раскрывая окружение и секреты.
3. Создать небольшой текстовый файл и сохранить его как артефакт сборки.
4. Иметь управляемый режим намеренной ошибки.
5. При этой ошибке завершаться неуспешно и не выполнять следующую стадию.
6. Иметь ограничение времени выполнения.

Проведите четыре эксперимента:

| Эксперимент | Ожидаемый результат |
| --- | --- |
| Обычный запуск | SUCCESS, известный agent, сохранённый артефакт |
| Намеренная ошибка команды | FAILURE именно на выбранной стадии, следующая стадия пропущена |
| Agent остановлен | Задание ожидает подходящий узел либо достигает заданного timeout; причина установлена |
| Controller перезапущен, agent восстановлен | Настройки и история сохранены, новый запуск успешен |

Ошибка синтаксиса или недоступность agent не засчитывается как успешная проверка обработки заданного отказа. Проверка YAML без запуска не доказывает работоспособность стенда.

## Что сдавать

Предлагаемые имена результатов:

| Файл | Содержание |
| --- | --- |
| `installation-plan.md` | Ваша инструкция с объяснениями, ссылками и внесёнными исправлениями |
| `sources.md` | Найденные первоисточники, разделы, версии и дата обращения |
| `environment.md` | Фактическая конфигурация и версии без секретов |
| `verification.md` | Четыре эксперимента, ID сборок, ожидаемые и фактические результаты |
| `reflection.md` | Ошибки, причины исправлений, границы решения и роль AI |

Конфигурация стенда и Jenkinsfile тоже входят в результат. Их формат определяется выбранной реализацией. Не прикладывайте дамп Jenkins home: он может содержать чувствительные данные.

В `sources.md` каждое решение связывается с конкретным разделом, например: «выбор Java → раздел документации → применимая версия → вывод». Просто список главных страниц недостаточен.

## Критерии зачёта

- Источники официальные, доступны для проверки и относятся к выбранным версиям.
- Собственная инструкция воспроизводима и различает выполненные и предполагаемые шаги.
- Все обязательные свойства стенда выполнены.
- Четыре эксперимента имеют наблюдаемые доказательства.
- Учащийся способен объяснить свою схему и диагностировать одну новую неисправность.

На защите объясните: где выполняется `sh`; где хранятся задания; что будет при удалении контейнера и при удалении volume; зачем agent собственная идентичность; чем «проверка нашла дефект» отличается от «проверка не запустилась».

## Подсказки выдаются по затруднению

Если застряли, сначала покажите свой план, найденный раздел документации, ожидаемый результат и фактическую ошибку без секретов. Наставник или AI сначала помогает сформулировать диагностическую гипотезу и найти нужный раздел. Готовая команда допустима как адресная помощь, но не заменяет объяснение и проверку.

Для AI-маршрута используйте [задание агенту](02-ai-assisted-setup.md). Общую последовательность компонентов смотрите в [плане окружения](00-environment-plan.md).
