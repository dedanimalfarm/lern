## Вывод

Есть полезные идеи для практических занятий: небольшое сквозное приложение, постепенное добавление security gates, тестирование, policy as code и продвижение между средами. Для нашего курса стоит написать собственный воспроизводимый стенд и использовать эти репозитории как учебные референсы и материал для аудита.

Первый репозиторий прямо помечен retired в README и направляет во второй. Второй содержит код к видеокурсу, но не является самостоятельным пошаговым учебником. В текущем Jenkinsfile основные стадии сборки, тестирования и безопасности закомментированы; активны две стадии проверки Slack с `exit 0`.

## Что полезно

| Элемент | Учебная ценность | Как использовать у нас |
| --- | --- | --- |
| Java-сервис и вызов NodeJS-сервиса | Простая зависимость между приложениями | Начальный пример; добавить исходники всех сервисов и сборку из своего Git |
| Jenkinsfile со стадиями Maven, SAST, SCA, DAST и deploy | Видно место проверок в цикле поставки | Разделить на последовательные работающие уроки |
| JUnit, JaCoCo, PIT | Различие наличия тестов, покрытия и способности обнаруживать ошибки | Добавлять дефект и доказывать, что тест его замечает |
| OPA/Conftest | Проверка конфигурации как кода | Написать требования и тестовые случаи до политики |
| DEV/PROD-манифесты, integration tests и rollback | Связь выпуска с проверкой результата | Продвигать один digest, ждать readiness, проверять откат |
| Trivy и ZAP-скрипты | Интеграция инструментов с gate | Различать PASS, найденный дефект и сбой инструмента |

В Java-приложении есть `/compare` и `/increment`. Этого достаточно для начальных тестов, но для обучения авторизации нужен сценарий с пользователями, ролями и владением данными. NodeJS упоминается как внешний готовый образ; его исходников в проверенном дереве второго репозитория нет.

## Что нужно переделать

### Установка и полномочия Jenkins

[install-script.sh](https://github.com/kodekloudhub/devsecops/blob/ba02940c13eaf5390a46aced8ad4f4ab1457cb27/setup/vm-install-script/install-script.sh) выполняет `kubeadm reset -f`, меняет настройки хоста и выдаёт Jenkins неограниченный sudo. Это не подходит как общий bootstrap на произвольной машине пользователя.

Наш маршрут: отдельная VM, controller и agent, установка по этапам и явная проверка уже существующей инфраструктуры. [Задание Jenkins](01-jenkins-setup.md) задаёт требования; свою инструкцию учащийся собирает по найденной официальной документации.

### Несогласованные версии

В `pom.xml` указаны Spring Boot 2.3.5.RELEASE и Java 8; runtime Dockerfile — adoptopenjdk/openjdk8. Скрипты Trivy закреплены на 0.17.2. CIS-скрипты используют Kubernetes 1.15, а install-script выбирает текущую stable minor-версию Kubernetes динамически.

Сам возраст версии не доказывает конкретную уязвимость. Практическая проблема — отсутствие согласованной матрицы и проверки окружения. Для нашего стенда нужны проверенный набор версий, digest, поддерживаемая Java Jenkins и соответствующий версии кластера benchmark. Текущая [матрица Jenkins](https://www.jenkins.io/doc/book/platform-information/support-policy-java/) должна проверяться отдельно от JDK приложения.

### Ошибочная обработка результата сканера

В [trivy-docker-image-scan.sh](https://github.com/kodekloudhub/devsecops/blob/ba02940c13eaf5390a46aced8ad4f4ab1457cb27/trivy-docker-image-scan.sh) и [trivy-k8s-scan.sh](https://github.com/kodekloudhub/devsecops/blob/ba02940c13eaf5390a46aced8ad4f4ab1457cb27/trivy-k8s-scan.sh) провалом считается только код 1. Другой ненулевой код попадает в ветку успеха.

Изолированная проверка: вместо Docker подставлена локальная команда-заглушка, возвращающая 125. Оба исходных shell-скрипта завершились с кодом 0 и сообщили об успешном сканировании. Docker и Trivy при этом не запускались. Проверка доказывает ошибку обработки кода возврата, а не работу конкретной версии сканера.

Это готовый сюжет лабораторной: «Проверка безопасности не выполнилась, но pipeline зелёный». Исправление должно различать успешно выполненный scan и ошибку инфраструктуры. Добавить отрицательный тест на недоступный инструмент.

Также первый скрипт извлекает FROM первой строки Dockerfile и проверяет базовый образ, а не собранный итоговый образ приложения. Во втором проверяется `imageName`; название «k8s scan» не означает проверку конфигурации всего кластера.

### Политика не равна требованию безопасности

[opa-k8s-security.rego](https://github.com/kodekloudhub/devsecops/blob/ba02940c13eaf5390a46aced8ad4f4ab1457cb27/opa-k8s-security.rego) требует NodePort для Service и проверяет `runAsNonRoot` только у `containers[0]`. При этом production Service в репозитории — ClusterIP. Это демонстрационное правило нельзя распространять на все окружения как универсальную норму.

Наша задача: вывести политику из модели угроз; проверить все применимые контейнеры, включая initContainers; добавить разрешённые и запрещённые примеры. Синтаксис старого Rego согласовать с текущим runtime по [руководству OPA по переходу на v1](https://www.openpolicyagent.org/docs/v0-upgrade).

### Слабая воспроизводимость и лишние побочные эффекты

- `zap.sh` использует weekly-образ и меняет права рабочего каталога на 777. Выберем закреплённый образ и корректные права для каталога отчётов.
- `kubesec-scan.sh` трижды отправляет один манифест во внешний API. Проверку лучше выполнять один раз на локальном закреплённом инструменте.
- Rollout-скрипты используют `sleep 60s`, короткий timeout и поиск текста успеха. Надёжнее проверять код завершения и состояние целевого rollout с осмысленным timeout.
- В закомментированном pipeline deployment и rollout-check запускаются параллельно. В своей реализации свяжем их зависимостью.
- `setup/jenkins-plugins/installer.sh` содержит демонстрационные admin/admin и печать создаваемого токена. В инструкции для пользователей нужны индивидуальная настройка и отсутствие секретов в логах.

## Связь с генерацией материалов

Референсный репозиторий даёт сценарий, но не становится единственным источником истины. Для каждого урока нужны четыре компонента:

1. Проверяемая цель и исходный дефект.
2. Официальная документация с версиями и конкретными разделами.
3. Собственная реализация лабораторной и независимые критерии проверки.
4. Два маршрута выполнения: вручную и с AI-агентом.

Например, сюжет «ошибка Docker стала PASS» превращается в урок о достоверности security gates. Генератор объясняет проблему на основании документации выбранного инструмента, а учащийся или его агент исправляет реализацию и предъявляет отрицательные тесты.

## Приоритеты переноса идей

Сначала: Jenkins и agent → приложение и тесты → ошибочный/исправленный gate → container build → тестовый Kubernetes. После этого — SBOM, подписи, provenance, identity CI и обнаружение runtime-событий. Их полноценной реализации в просмотренном дереве второго репозитория не найдено.

Уведомления Slack и service mesh оставляем дополнительными темами. Они не заменяют надёжное выполнение проверок, минимальные права и доказательства выпуска.
